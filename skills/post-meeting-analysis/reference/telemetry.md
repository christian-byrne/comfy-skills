# Telemetry (Phase 8)

Telemetry is optional. The pattern: the agent writes a structured JSON summary; if you have a SessionEnd hook (or equivalent automation) of your own, it can process that summary into whatever sinks you track skill runs in.

## How It Works

1. Agent writes `.post-meeting-run-summary.json` in the repo root after Phase 6
2. If wired, your own SessionEnd hook (or similar automation) fires at session end
3. The hook reads the summary file and appends to:
   - `skills/post-meeting-analysis/run-log.yaml` (structured YAML entry)
   - any other skill-execution log you maintain
4. The hook deletes the summary file after processing

If no hook is wired, the summary file simply persists on disk — you can read it manually or process it however you like. If the session ends abnormally, the summary file also persists and can be picked up by whatever adherence/cleanup check you run, if any.

## Summary JSON Schema

Write to `$REPO_ROOT/.post-meeting-run-summary.json`:

```json
{
  "date": "2026-04-22",
  "meeting_id": "fireflies-abc123",
  "meeting_title": "Bert & Baira Weekly",
  "meeting_date": "2026-04-22",
  "attended": true,
  "rerun": false,
  "rerun_note": null,
  "meeting_type": "recurring-1on1",
  "action_items_extracted": 7,
  "decisions_extracted": 3,
  "topics_extracted": 4,
  "open_questions": 2,
  "fact_check_claims": 4,
  "fact_check_internal": 2,
  "fact_check_external": 2,
  "dispatch_tasks_generated": 3,
  "comms_profiles_matched": 2,
  "comms_profiles_created": 0,
  "comms_interactions_logged": 2,
  "recurring_series": "bert-baira-weekly",
  "carried_forward_items": 1,
  "stale_items": 1,
  "completed_items_from_prior": 2,
  "dropped_items": 0,
  "dashboard_regenerated": true,
  "handoffs": {
    "agent_dispatch": false,
    "slack_posted": false,
    "gws_calendar": false,
    "gws_email": false
  },
  "outputs_dir": "outputs/2026-04-22-bert-baira-weekly/"
}
```

All fields optional except `date` and `meeting_id`. Missing fields default to `0`, `null`, `[]`, or `false`.

## Run-Log Entry (Generated by Your Hook)

If your hook is wired, it can convert the JSON summary into a YAML entry appended to `skills/post-meeting-analysis/run-log.yaml`:

```yaml
- date: '2026-04-22'
  meeting_id: 'fireflies-abc123'
  meeting_title: 'Bert & Baira Weekly'
  meeting_type: 'recurring-1on1'
  action_items: 7
  decisions: 3
  fact_checks: 4
  dispatch_tasks: 3
  comms_synced: 2
  carried_forward: 1
  stale_items: 1
  handoffs: [agent_dispatch]
  thread_id: 'T-...'
```

## Skill Execution Record (Optional, Generated by Your Hook)

If you keep a broader skill-execution log elsewhere in your setup, the hook can append a record like:

```json
{
  "timestamp": "2026-04-22T15:30:00Z",
  "skill": "post-meeting-analysis",
  "thread_id": "T-...",
  "outcome": "completed",
  "files_changed": 5,
  "duration_estimate": "medium"
}
```

## Fallback if There Is No Hook

Without a hook, the summary JSON just persists at `.post-meeting-run-summary.json` in the repo root. Read it manually, or have whatever cleanup/adherence check you run pick it up.

## Metrics to Track Over Time

Use `jq` against `run-log.yaml` or the summary JSONs to analyze:

- Average action items per meeting type
- Fact-check hit rate (claims verified vs total)
- Dispatch task completion rate (cross-reference with your own agent-dispatch telemetry, if you track it)
- Carried-forward staleness trend for recurring meetings
- Comms profile coverage (matched vs created vs skipped)
